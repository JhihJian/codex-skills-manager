# 技能验证工作台设计

## 目标

帮助使用者通过页面检查当前启用技能的设计缺陷，而不是先填写一份问题上报问卷。工作台必须把发现过程和正式质量结论分开。

## 工作流

1. 使用者选择当前启用的技能。
2. 页面只读检查当前 `SKILL.md` 及该技能明确要求的参考文件。
3. 页面展示检查观察、预期行为、可能影响、隔离复现步骤和已有一手证据。
4. 使用者可以按相同步骤在隔离任务中复核。只有尚未收录的新线索才进入“提交线索”页面。

页面不显示内部目录名、版本哈希、Case ID 或质量状态码。当前默认收录三个已完成真实验证的规则：裸仓库日常模板的 Bash 缺口、Gradle wrapper 的 sed 转义错误和多角色审议记录模板缺失。

## 证据边界

验证 API 只读取当前启用且非系统的技能。每条“已复现”发现必须同时有当前说明或参考文件中的命中条件，以及 `docs/skill-real-use-validation.md` 所记录的隔离真实验证依据。

验证结果不是技能失败率、合同检查失败、体验判断或正式质量结论。`skill-problem-discovery` 仍是独立的人工线索通道，并被正式反馈快照排除。

## 维护

修复技能后，同一规则会在当前内容不再命中时显示为未发现，不应保留为历史失败。新增规则需要补充当前版本可验证条件、隔离复现步骤、预期、影响和一手证据，再添加到 `skill_validation_detail()`。
